# Performance result: Xeon Silver 4216 CPU scaling

This result was collected on 2026-08-13 to demonstrate Treetop REST's CPU-affinity matrix and provide a reproducible
baseline. It is a characterization of one node and fixed test fixture, not a service-level objective or capacity
promise.

## Interpretation

- Exact topology matters. At concurrency 2, the SMT-sibling set `0,16` produced 7,395 simple authorizations/s,
  about 73% of the 10,096/s from separate physical cores `0-1`.
- The liveness path approached a loopback/client/server plateau after two physical cores. Simple authorization
  throughput continued from 5,758/s on one CPU to 34,782/s on eight CPUs at the allocation's maximum concurrency.
- One batch-128 request improved from 140 requests/s with one Rayon thread to 420 requests/s with four threads; its p95
  fell from 7.18 ms to 2.40 ms.
- At maximum concurrency, batch-128 throughput reached only 532 requests/s on eight CPUs while p95 rose to 18.69 ms.
  Queueing and simultaneous batch parallelism therefore matter; the concurrency-1 result is the cleaner within-batch
  scaling comparison.
- The 1,000-request sample is appropriate for this example, but repeated 5,000-or-larger runs should be used for
  capacity planning and strong p99 claims.

## Reproduce

Run the exact allocation matrix with:

```bash
TREETOP_PERF_CPU_SETS='0;0,16;0,1;0-3;0-7' \
TREETOP_PERF_SAMPLES=1000 \
TREETOP_PERF_WARMUP=200 \
TREETOP_PERF_LAYOUTS=default \
TREETOP_PERF_OUTPUT_DIR=performance-results/my-run \
scripts/run-performance-matrix.sh
```

The five full anonymous JSON reports also contain raw per-request durations. They were inspected before this compact
summary was published but are not committed because the raw samples add almost 1 MiB and do not improve the permanent
comparison. The report intentionally excludes hostname, username, addresses, paths, policy data, labels, and request
bodies.
